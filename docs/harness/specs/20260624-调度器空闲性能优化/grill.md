## 当前理解

- 需求目标：降低后台调度线程在空闲时的常驻开销（实测 CPU/能耗偏高），不损失有任务时的灵敏度。

- 主要非目标：不做完全事件驱动重构，不改存储格式。

## 已确认结论

- 根因是空闲 tick 的全量磁盘读写 + JSON 序列化 + 噪音日志，而非 CPU 死循环空转。
- 用户要中等范围：最小改动 + 自适应间隔；噪音日志可删/降级。

## 推荐假设

- 空闲上限间隔取 60s（参考 `poll_interval_seconds`）。
- 仅做范围 1~3 即可消除绝大部分空闲 I/O；自适应间隔为增量收益但需唤醒配套。
