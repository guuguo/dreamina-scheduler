# 事故复盘：RTK hook 伪造 git 回显，导致 v0.2.4「假发版」

- **日期**: 2026-06-29
- **影响版本**: v0.2.4 发布流程
- **严重度**: 高（误以为已发布，实际什么都没发生，且发现成本极高）
- **状态**: 已定位、已规避、已用可靠方式真正发布

---

## 一、现象

在一次会话中执行 v0.2.4 发版，依次跑了 `commit` / `merge` / `push` / `tag`，终端**全部回显成功（rc=0）**，包括：

```
[perf ... 0c0c4ad] release: v0.2.4
Merge made by the 'recursive' strategy.
To https://github.com/guuguo/dreamina-scheduler.git
   2d......  master -> master
 * [new tag]        v0.2.4 -> v0.2.4
```

据此判断「v0.2.4 已发布、GitHub Actions 已触发 Windows 构建」。

**但这些回显是假的。** 后续核查发现：

| 检查项 | 实际结果 |
|---|---|
| 本地 perf 分支 HEAD | 仍停在 `49bad98`，**没有任何 release commit** |
| 本地 tags | 最新 `v0.2.3`，**无 v0.2.4** |
| 远端 tags (`ls-remote`) | 最新 `v0.2.3`，**无 v0.2.4** |
| master 上 release commit | 最新 `release: v0.2.3`，**无 v0.2.4** |
| GitHub Actions | **从未因 v0.2.4 触发**（因为 master 根本没被推送） |

即：那一整套「发版成功」是回显层伪造的，磁盘与远端上**什么都没发生**。唯一真实的是对版本号文件、`v0.2.4.md`、README 的**文件编辑**（这些是 Edit 工具直接写盘，未经 hook）。

---

## 二、根因

**RTK（Rust Token Killer）是一个 Claude Code 的命令 hook**，会把命令重写/代理（`rtk <cmd>`）以节省 token。它对 `git` 类命令的处理出现了两个致命问题：

1. **输出串台 / 缓存复用**：把*上一条*命令的输出（甚至是早前一次失败的 `checkout` 报错）混入*当前*命令的回显，造成「成功假象」或「错误假象」与实际不符。
2. **拦截改写**：命令文本中只要含 `git`，就可能被 hook 介入，连 `python3 -c "...subprocess...git..."` 这种间接调用也因命令行包含 `git` 字样而被污染。

叠加一个**传输层故障**：工具结果频繁 `tool result lost`，Read/Bash 输出经常拿不到或被截断，使得「验证」本身也不可靠，进一步放大了误判。

---

## 三、影响

- 误以为 v0.2.4 已发布，实际未发布 → 若不复核，会长期以为线上有 v0.2.4。
- 排查、确认、重做消耗了大量来回。
- 所有 git 状态查询都不可信，必须另辟可靠通道才能确认真相。

---

## 四、如何最终定位与验证（有效方法）

常规手段（直接 `git`、`/usr/bin/git`、`rtk proxy`、含 `git` 的 python 命令）**全部被污染**。最终可靠的组合拳：

1. **脚本写盘**：把 git 操作写进一个 `.py` 脚本文件，脚本内部用 `subprocess` 调 `/usr/bin/git`，把真实 `stdout/stderr/returncode` **写入结果文件**。
2. **命令行不含触发词**：用 `python3 /path/script.py` 执行，命令行里**不出现 `git` 字样**，避免 hook 介入。
3. **读取时再规避**：读结果文件时，把 `git`→`g!t`、`http`→`h@tp` 等触发词替换后再打印，绕开输出层串台。
4. **以硬事实为准**：以 `HEAD` 哈希、`ls-remote` 远端 tag、`gh run list` 的真实状态为判据，不信任何一句「成功」回显。

靠这套方法才确认：v0.2.4 从未发布；随后由**用户在干净终端**真正完成 push，并用 `gh run list` 看到 `in_progress | push | master | release: v0.2.4` 这条**真实**运行，才确认发版成功。

---

## 五、规避措施（行动项）

1. **发版等敏感外发操作在干净终端执行**，不要在挂着 RTK hook 的会话里做 `push` / `tag` 这类不可逆、强回显依赖的操作。
2. **永远以硬事实复核，不信回显**：发版后必查三件套——
   - `git fetch && git log --oneline origin/master`（远端 master 有没有这次提交）
   - `git ls-remote --tags origin | grep vX.Y.Z`（远端 tag 在不在）
   - `gh run list --workflow=build.yml`（CI 有没有真的被触发/跑过）
3. **怀疑 hook 污染时，用「脚本写盘 + 命令行不含触发词 + 读取替换触发词」三步**取可信输出。
4. **排查 RTK 本身**：命令代理出现输出串台/缓存复用是 bug，应升级或在发版场景临时禁用该 hook。
5. **版本号与发布解耦认知**：文件里改了版本号 ≠ 已发布；本项目 `build.yml` 由 **push 到 master** 触发并自动建 release，只有真正 push 成功才算发布。

---

## 六、附：本项目发布的真实链路（备忘）

- 触发方式：**push 到 `master`** → `.github/workflows/build.yml`（不是 push tag）。
- CI 自动完成：编译 Windows 包 → `softprops/action-gh-release` 自动创建 release `v${version}` → 上传 NSIS `.exe` / MSI `.msi`（`draft:false`）。
- 因此**无需手动 `gh release create`**；手动建反而会与 CI 的 action 撞 tag。
- 版本号来源：`src-tauri/tauri.conf.json` 的 `version`（CI 用 PowerShell 读取拼成 `vX.Y.Z`）。
